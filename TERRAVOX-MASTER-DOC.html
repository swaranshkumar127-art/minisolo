4.2 VoxelWorld — the voxel engine

  • Single UProceduralMeshComponent ("VoxelMesh") owned by AVoxelWorld, created in the constructor (CDO) — guaranteed registered & rendered at spawn.
  • Section-per-chunk: ChunkSections map = chunk key → PMC section index (phase 1 stages all columns, then meshes each chunk). RenderDistance 4 → 9×9 = 81 chunks.
  • Chunk: 16×16 columns × TerrainDepth = 64 blocks tall.
  • Height field: two octaves of Perlin noise — H = 24 + HeightScale(22) * (N + 0.6·N2), clamped to [1, 63].
  • Column fill: grass (top) / dirt ( +1) / stone below, bedrock at y=0.
  • Taiga pines: deterministic sparse trees (10% chance) — log trunk 4–6 tall + spruce crown.
  • Meshing: greedy-ish by culling internal faces (6-sided, IsSolid neighbor test); vertices are (X, Y=height, Z).
  • Face winding explicitly reversed so fronts face outward in UE (verified against real renders).
  • Vertex colors = per-block palette + per-face sun-shading (down 0.68, side 0.82/0.9) + per-block grain noise. Block palette:
IDBlockRGB
1Grass (taiga green)(104, 158, 64)
2Dirt(132, 94, 66)
3Stone(124, 124, 130)
4Plank(164, 132, 74)
5Pine log(101, 73, 51)
6Pine leaves(52, 112, 40)

Public API surfaced: GetBlock / GetTerrainHeight / SetBlock / RebuildChunksInRadius; tunables RenderDistance, TerrainSeed (1337), HeightScale (22).

4.3 TerraVoxGameMode — sky, day/night, camera rig
  • Atmosphere actor set (all spawned at runtime, no blueprints needed):
    • Sun — directional, intensity 3.4, color (1.0, 0.97, 0.90), SetAtmosphereSunLight.
    • Sky Atmosphere — real day-sky gradient + horizon haze.
    • Exponential Height Fog — density 0.003, heightfalloff 0.05, inscattering (0.56, 0.62, 0.68).
    • Sky Light — ambient bounce, real-time capture off, intensity 0.6 (kills pitch-black shadows).
  • Day/night cycle (240 s ≈ 4 min loop): elevation sin(phase·2π)·70°, azimuth rotates 360°; sun intensity 0.9→3.5, color lerps warm-day ↔ cold-blue-night; fog color/density shifts too.
  • Flat-spot camera pin (the fix that made everything visible):
    1. At t>1 s scan the world grid (gy 2..55, gx 2..40 step 3) for the flattest spot (min sum of 4-neighbour height deltas) → FlatSpot, ground H.
    2. Freeze the pawn: disable actor collision + disable all UMovementComponent ticks.
    3. PC0->ClientSetLocation(FlatSpot.X, FlatSpot.Y, H+3.5, rot(-8°,0,0)), then a 0.5 s repeating re-pin timer so nothing can knock the view off-frame.
  • One-shot screenshot rig at t>6 s: dumps DBG CAM POV, runs show Default, then 0.8 s later HighResShot 1280x720 → Saved/Screenshots/WindowsEditor/.
  • One-shot DBG terrain box at t>2 s logs mesh bounds/transform (diagnostic).

4.4 PlayerPawn — the FPS survivor

  • Spring-arm (length 0) + FPS camera; pawn-control rotation yaw.
  • Movement tuned: gravity 1.8, jump 430 up/velocity, air control 0.28, walk 440.
  • Input (see §4.6): MoveForward/Right, Turn, LookUp, Jump, FireL = break, FireR = place plank.
  • Raycast to ECC_WorldStatic within 7 m reach; break = SetBlock(...,0), place = SetBlock(...,4) on the opposite face; falls back to attachment-root actor (for PMC pieces).

4.5 Config / rendering posture

  • GlobalDefaultGameMode = TerraVoxGameMode; Entry map (empty template) as the only map — world is 100% C++ spawned.
  • Hardware target: Desktop + Maximum quality only nominally; real renderer is tuned for an iGPU: distance fields off, virtual shadows off, GI method 0, smooth framerate, min 30 FPS.
  • Uniform unlit vertex-color material (engine-shipped /Engine/EngineDebugMaterials/VertexColorMaterial) — chosen because runtime async-lit shader compile caused minutes of invisible terrain on this GPU.

Fixed by using the engine's precompiled runtime lit vertex-color material, launching with -unattended (kills the PostProcessQuality dialog that swallowed input/focus), 81-chunk world, skylight ambient; day/night cycle added.

Next failure: pure blue screen — sky renders, terrain does not. The lit runtime material was still failing asynchronously for the terrain mesh. Final fix: swap to the engine's unlit VertexColorMaterial (always precompiled, shows vertex colours directly). Day/night retained. From here on the terrain had vertex-color shading baked into the mesh itself.
STAGE 5 · 29 Sep 16:32 → 16:49 · commit b71d36a — THE BREAKTHROUGH
"TERRAIN VISIBLE"
Hours of pixel-science debugging (full checklist in §6) ended with two discoveries that finally made the terrain appear:
(1) The voxel world builds with +Y as height, but UE's camera is +Z-up. The terrain was literally a rolled vertical slab in front of / under the camera. Fix: spawn the world actor with FRotator(0,0,90) (roll +90°) so local Y→world Z. The pitch -90° idea does not map Y up correctly (local Y stays world Y).
(2) The pawn was being teleported / was free-falling to world Z ≈ -5382…-7193 — miles below the terrain — so the camera was aimed at nothing. Fix: the flat-spot camera pin (§4.3).
Result — verified in-screenshot: blue sky on top, green voxel ground on the bottom, stable DBG CAM pos=(26,14,24.5). Debug probe objects removed. Project committed.
Parallel · the UBT boot-war
The build/launch intermittently deadlocked at "Launching UnrealBuildTool… ValidatePlatforms". Eventually diagnosed as a .NET apphost problem with the engine's bundled UBT. Workaround chain: kill all UnrealEditor/dotnet/cmds, delete %LOCALAPPDATA%\UnrealBuildTool, run the ValidatePlatforms step manually once with DOTNET_ROOT pointed at the engine's 10.0/win-x64 dotnet — then boots became fast. (Full recipe in §7.)

6.2 The discipline that cracked it

Because the AI could not see screenshots, we built a pixel-probing renderer truth-loop:

  1. Delete old log + screenshots before each launch (stale files caused false alarms).
  2. Log machine-readable markers at every stage (VW:, TERRAVOX, DBG CAM…).
  3. At t>6 s the game self-screenshots with show Default + HighResShot 1280x720.
  4. Analyse the PNG pixel-by-pixel with System.Drawing: a 20×12 region classifier (b=blue sky, G=green, g=grey, Y=yellow, R=red, W=bright) plus a 32-bucket colour-cluster histogram.
  5. From the region map we could infer the scene composition (e.g. "sky rows on top, green band on bottom = terrain visible; all-blue = camera pointing at void; all-grey = material failed").

Also used staged "truth-table" probes (static vs procedural-mesh cubes, basic vs vertex-colour materials, placed at known coordinates) to isolate exactly which render path worked — that's how the unlit material was proven.

6.3 The axis confusion (why it took so long)

The world generator writes block (X, Y, Z) with Y used as altitude (classic Minecraft layout) while UE positions actors in +Z-up. This single mismatch produced every "invisible terrain" moment and even made GetTerrainHeight(X, Z) misuse the wrong axis in camera logic. The correct mental model, verified on screen:

VoxelWorld spawned with FRotator(0, 0, 90)
  voxel grid (X, Z)  ==  world (X, -Y)
  voxel height (local +Y)  ==  world +Z
  GetTerrainHeight(X, -worldY)  ==  ground world-Z  (eye = H + 3.5)

Very important: a pitch of -90° does NOT help — local Y stays world Y. Roll +90° is the only mapping that lifts voxel-height into world-up.

7.4 UE 5.8 gotchas (memory, so we never waste hours again)

  • FVector(a, b) 2-arg form fails to compile in some contexts → always use 3 args.
  • APlayerCameraManager::SetDesiredRotation does not exist → use ClientSetLocation + control rotation.
  • Runtime-created dynamic materials async-compile → fragile on iGPU; prefer engine precompiled materials.
  • CreateMeshSection(bCreateCollision=true) publishes collision data but the pawn still free-falls through terrain → component collision posture + complex-as-simple is next to fix (§8).
  • The engine may teleport the pawn to map default-spawn after the map reports loaded — always tolerate late movement.
  • Module .Target.cs must add ProceduralMesh (and mirror in Build.cs) or non-editor targets fail to link.

§8Current blockers & known bugs (honest)

  • Terrain collision / pawn free-fall (blocking gameplay). The terrain PMC sections include cooked collision bodies, but the Character's capsule doesn't land on them — the pawn falls through to the world bottom. Until fixed, the pawn stays frozen and the camera is cinematic-pinned. First candidate fixes (in order, all cheap to try):
    1. On the PMC: SetCollisionEnabled(QueryAndPhysics) + SetCollisionObjectType(ECC_WorldStatic) + SetCollisionResponseToAllChannels(ECR_Block); for complex-as-simple, PMC needs bUseComplexAsSimpleCollision = true (or rely on its auto-built simple collision).
    2. Consider a Character CapsuleComponent ground probe on OnActorHit to debug landing.
    3. Fallback: build per-chunk runtime UStaticMesh from the same FMeshDescription and let the engine make a proper body (heavier, but 100% standard).
    4. Very last resort: voxel ray-casts for gravity + manual ground clamp (full own-physics, most control).
  • Camera is currently cinematic, not gameplay — by design until collision lands.
  • Material is unlit vertex colour — correct for now, will upgrade to a nicer lit material after gameplay works (with prewarm so the iGPU doesn't go invisible).
  • No game feel — no sounds, no UI, no particles yet (all planned, ordered).

==================== AXIS TRUTH (super important, took hours) ====================
Voxel grid is Y-UP (block y = altitude), UE camera is Z-UP. AVoxelWorld must be spawned with
FRotator(0.f, 0.f, 90.f) (ROLL +90). THEN: voxel grid (X, Z) == world (X, -Y); voxel local +Y (height) == world +Z;
ground height for world (X,Y) = GetTerrainHeight(X, -Y); eye Z = H + 3.5. A pitch of -90 does NOT map Y up.
This mapping is verified on-screen (green terrain + blue sky + horizon, stable camera).

11.4 FAQ / mental models

Why is the material unlit?Runtime lit materials async-shader-compile forever on this iGPU, leaving the terrain invisible for the whole session. Engine precompiled unlit VertexColorMaterial appears instantly and honours the baked vertex-colour shading.
Why not a marketplace voxel plugin?Deliberate decision (VISION.md): full control + learning. The custom engine already does heightmap + trees + culled meshing + break/place + colour palette.
Why is the camera frozen instead of first-person?Temporary. The pawn falls through the terrain (collision bug, §8). Once a Character can stand, the pin/unfreeze swap is a two-line change and first-person gameplay returns.
Why Entry map / zero assets?Everything is spawned in C++, so the project is tiny, fully scripted, and deterministic. Assets (materials, Niagara, UI) will be added per feature. This fits the "merge = playable" rule.
Windows-only? Why D3D11?Machine is i5-8365U + Intel UHD 620. D3D11 is the only reliable backend here; built for desktop (Development editor).
